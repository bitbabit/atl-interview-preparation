Evidence & Numbers

Collect only defensible metrics. Never invent a percentage to make an answer sound stronger.

Numbers to collect

  • MySQL utilization before and after the production fix.
  • Incident duration and time to identify root cause.
  • GraphQL API hit/latency/load change after caching.
  • Number of GraphQL APIs where caching was added.
  • Number of synthetic checks / critical journeys monitored.
  • Number of releases processed through the release-review workflow.
  • Largest number of changed files in one release.
  • Unexpected/unowned files caught before production.
  • Release-review time before vs after automation.
  • Number of developers using the process.
  • Production defects caught before release that can be tied to these controls.

How to use numbers

Good

“The generated change register contains every changed file in the release diff, so each file must be mapped to an owner/ticket before release.”

Avoid

“AI catches 99% of issues.” Unless this was actually measured, do not say it.

When no metric exists

State the observable result, then mention the metric you would track next.
