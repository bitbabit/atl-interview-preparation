Production Scenarios

Use repeatable reasoning patterns so you can answer unfamiliar incident questions without memorizing scripts.

Default incident framework

Impact → Evidence → Isolate → Root Cause → Lowest-risk Fix → Verify → Prevent.

Start with affected users/business flow and blast radius. Then use the smallest set of reliable signals—logs, metrics, traces, process/query data—to narrow the problem. Do not jump straight to a code change if configuration or data can safely recover the service.

Scenario: MySQL node utilization

Situation: CPU/database utilization increased on the first node.

Reasoning: First understand why the load is concentrated there; SELECT traffic was primarily handled by that node. Process-list evidence showed repeating queries but not yet enough proof. strace on application processes exposed one long-running process repeatedly executing the query in a loop.

Recovery: Correct the problematic production data and terminate the stuck process; monitor utilization afterward.

CTO follow-ups: Why strace? Why not only kill the process? What prevention would you propose? How would you set a safe timeout?

Scenario: QC cannot reproduce

Use observability to reconstruct the actual user journey instead of asking QC to repeat random attempts. Capture identifiers and sequence, compare the journey with normal flows, then reproduce under controlled conditions.

Answer pattern: “QC could not reproduce it, so I used our custom logs to reconstruct the user journey. That gave us the exact sequence needed to reproduce and investigate the issue.”

Scenario: emergency production fix

1. Stabilize

Reduce customer impact using the least risky reversible action.

2. Preserve evidence

Capture logs/process/query information before destroying useful evidence.

3. Decide deployment vs config/data

If configuration/data can safely fix the immediate issue, a code deployment may not be required.

4. Validate

Smoke check critical flows and compare the same metrics that showed the incident.

5. Permanent prevention

Reproduce in a lower environment where possible; implement/test the durable fix and update monitoring/process controls.

Scenario: release risk

Use the release workflow to answer: what changed, which module/user flow is affected, what should be tested, who owns each file, and which changes deserve deeper manual review. AI helps enumerate and structure risk; humans make the release decision.

Common CTO traps

“Would you always reproduce production issues locally before fixing?”

No. For an active incident, restoring service safely can come first. Permanent code fixes should be reproduced/tested in lower environments where practical.

“Why change data directly in production?”

Only when the data is clearly the trigger, the change is narrow and understood, access/process allows it, and it is lower risk than a code deployment. Record and validate the change.

“How do you know the root cause rather than a symptom?”

Because removing or correcting the identified cause changes the observed system behavior, and the same evidence path explains how the symptom was produced.
